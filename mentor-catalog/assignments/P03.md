# P03 — Сетевая диагностика сервиса

Неделя 3. 10–12 часов. До начала: Принят P02.

На сервере сервис отвечает, а с ноутбука недоступен. Нужно построить карту соединения и научиться различать ошибки имени, маршрута, порта и приложения.

## Что важно понять

DNS сопоставляет имя с адресом, TCP соединяет конечные точки IP:порт, HTTP описывает запросы и ответы. Успешный ping не доказывает работоспособность HTTP. Запись hosts обрабатывает локальный resolver, но она не становится записью DNS.

## Задание

1. Нарисуй в docs/network.md путь ноутбук → виртуальная сеть → VM → процесс. Укажи IP, маску, шлюз и порт; объясни адреса 127.0.0.1 и 0.0.0.0.
2. Сравни запрос к loopback на VM, SSH-туннель с ноутбука и запрос к IP VM. Объясни, почему сервис с bind на loopback напрямую недоступен извне.
3. Настрой локальное имя catalog.test через hosts для следующего проекта. Сравни getent hosts с dig; отдельно проверь публичное DNS-имя.
4. Собери диагностическую последовательность: resolver, маршрут, listening socket, соединение, HTTP-ответ, журнал. Используй ip, ss, curl и доступный DNS-клиент.
5. В лаборатории настрой firewall с разрешенным SSH до включения правил. Сохрани консоль VM как путь восстановления; открывай только порт, нужный текущему упражнению.
6. Сравни три симптома: неверное имя, connection refused, HTTP 404. Для каждого сохрани команду, наблюдение и вывод.

## Приемка

- Менти объясняет путь запроса и показывает адрес процесса через ss.
- Три класса отказов различены по фактам, а не по одной команде ping.
- После изменения firewall сохраняется SSH-доступ, список разрешенных портов документирован.
- В документации hosts не назван DNS-сервером; назначение и ограничение SSH-туннеля понятны.

## Учебная неисправность

- Подставь неверный порт в curl и неверный IP в локальную запись hosts. Для каждой неисправности составь цепочку гипотеза → проверка → результат → исправление.
