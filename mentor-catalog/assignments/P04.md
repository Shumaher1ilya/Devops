# P04 — Веб публикация и управляемый релиз

Неделя 4. 10–12 часов. До начала: Принят P03.

Команда хочет обращаться к каталогу по имени и обновлять его без потери предыдущей рабочей версии.

## Что важно понять

Reverse proxy принимает клиентский запрос и обращается к backend. Ответ 502 обычно связан с проблемой взаимодействия с upstream и требует проверки логов. TLS включает шифрование и проверку подлинности сервера; просто отключить проверку сертификата недостаточно.

## Задание

1. Поставь Nginx перед сервисом: клиент → Nginx → 127.0.0.1:8080. Настрой server_name catalog.test, access log и error log.
2. Проверь конфигурацию до reload. Продемонстрируй /healthz, /version, /items и неизвестный маршрут через proxy.
3. Настрой TLS в локальном стенде: сертификат с SAN catalog.test, проверка через curl --cacert с лабораторным CA или доверенным учебным сертификатом. Закрытые ключи держи вне репозитория. Публичный домен и ACME — дополнительный вариант.
4. Разверни две версии в отдельных каталогах releases/<tag>. Данные храни вне releases. Переключай current на нужный release и перезапускай сервис.
5. Добавь smoke-проверку версии и /items, а при неудаче вручную верни предыдущий release. Запиши порядок отката.
6. Проведи контроль месяца: повтори запуск на чистом снимке VM и защити решения за 15 минут.

## Приемка

- Через Nginx доступны нужные маршруты, backend остается на loopback.
- TLS-проверка завершается без -k; имя сертификата совпадает с catalog.test.
- Демонстрация v1 → v2 → v1 меняет /version и сохраняет данные.
- Ментор может воспроизвести релиз по инструкции; матрица обновлена после защиты.

## Учебная неисправность

- Укажи неверный upstream-порт в учебной конфигурации. Сопоставь 502, error log и доступность backend напрямую, затем верни рабочую конфигурацию.

- infra/nginx/, docs/release.md, docs/tls.md, журнал переключения версий и исправления 502.
