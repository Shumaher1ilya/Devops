# P05 — Автоматизация эксплуатации

Неделя 5. 10–12 плюс резерв для новичка часов. До начала: Принят P04; базовые переменные, условия, циклы и функции.

Проверка здоровья и выпуск релиза отнимают время. Команда просит маленькие утилиты с понятными ошибками и предсказуемым повторным запуском.

## Что важно понять

Код возврата позволяет автоматизации отличить успех от сбоя. stdout предназначен для результата, stderr — для диагностики. Идемпотентная операция при повторном запуске не создает лишних изменений; set -e сам по себе не заменяет обработку ошибок.

## Задание

1. Напиши Bash-утилиту healthcheck.sh: URL аргументом, ограниченные connection/total timeout, проверка HTTP 200 и поля status, ненулевой код при ошибке.
2. Напиши deploy.sh <release-dir>: проверить входной каталог, сохранить предыдущую ссылку, переключить release, перезапустить сервис, выполнить healthcheck, вернуть предыдущую версию при неуспехе. Используй только лабораторный каталог.
3. Добавь проверку аргументов и кавычки для путей с пробелами. Не логируй содержимое секретного окружения.
4. Напиши Python-утилиту analyze_logs.py для JSONL приложения: общее число запросов, число ответов 5xx, частоты путей. Некорректные строки считай отдельно и показывай предупреждение.
5. Подготовь тестовые логи: пустой файл, корректные строки, битый JSON, отсутствующий файл. Добавь автотесты ожидаемых счетчиков и ошибок.
6. Запусти утилиты дважды, объясни изменения. Оформи docs/automation.md с примерами успешного и неуспешного вызова.

## Приемка

- Неверный URL и timeout дают ненулевой код, успешный запрос — нулевой.
- Неудачный релиз возвращает предыдущую рабочую версию и сообщает об ошибке.
- Парсер верно считает заранее подготовленную выборку; битые строки не исчезают незаметно.
- Путь с пробелом и отсутствие аргументов проверены, тесты запускаются одной командой.
